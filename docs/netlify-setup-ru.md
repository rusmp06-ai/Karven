# KARVEN: Netlify + Supabase

Адаптация сохраняет дизайн и функции CRM. Проверки выполняются на изолированных данных. Реальный проект Supabase ещё не подключён; публикация в Netlify требует действий в аккаунте владельца.

## Как устроено

- Next.js работает через адаптер Netlify, Node.js 24. Статический экспорт не используется.
- SQL-запросы выполняются только сервером через Supabase **Session pooler, порт 5432**. Transaction pooler на 6543 не подходит: блокировки запросов сессионные.
- Постоянной блокировки всего приложения больше нет. Каждый запрос получает общую блокировку PostgreSQL до проверки сессии и освобождает её после завершения. Это координирует разные экземпляры функций, включая восстановление и Telegram. Проверка сессии, чтение и бизнес-транзакции используют одно закреплённое соединение запроса, в том числе при обращении через разные экземпляры адаптера. Вложенные вызовы используют ту же область запроса. Бизнес-транзакции дополнительно сериализуются отдельной транзакционной блокировкой.
- Копии хранятся в таблице `karven_archive.backups`, отдельно от восстанавливаемых бизнес-таблиц. Это закрытая область той же PostgreSQL, а не отдельный платный сервис. Схемы `karven` и `karven_archive` не выдаются клиентским ролям; включён RLS. Обновление приложения не удаляет копии. Копии расходуют квоту базы Supabase: скачивайте их и сохраняйте также вне проекта. Это не защита от потери всего проекта Supabase.
- В Netlify копия ограничена **3 МиБ**: запас для лимитов запросов/ответов функций. Проверка копии использует временную PGlite в `/tmp`, затем удаляет её; постоянные данные там не хранятся. Локальная версия сохраняет прежний лимит 64 МиБ.
- Ключ шифрования Telegram берётся из серверной переменной `CRM_TELEGRAM_KEY`. Генерировать новый ключ при каждом развёртывании нельзя: старые токены перестанут расшифровываться. Токен бота и ID чата вводятся через настройки CRM.
- После создания брони попытка доставки запускается через Next.js `after`, после ответа пользователю. Сохранение не ждёт сетевого ответа Telegram. При недоступности фонового запуска очередь остаётся в базе для Scheduled Function. Неудача доставки не отменяет бронь. Scheduled Function `telegram-dispatch` проверяет оставшуюся очередь каждые пять минут, до трёх сообщений за запуск. Расписание работает в production, а не в Deploy Preview. Неопределённая доставка требует ручной проверки чата и повтора; автоматически повторяются только подтверждённые ограничения частоты Telegram.
- Ожидающий запрос проверяет блокировку неблокирующим способом, закрывает соединение перед повторной попыткой и ограничивает ожидание. После ответа сокет закрывается с ожиданием завершения, а не оставляется таймеру пула: Netlify может заморозить процесс раньше срабатывания таймера. В Netlify также заданы серверные таймауты бездействия 30 секунд на случай прерывания функции. Обычно запрос занимает одну сессию; только страховочная копия внутри восстановления временно использует дополнительное соединение, чтобы пережить откат. Ошибка первоначального подключения не кэшируется навсегда.
- Постоянный сервер и `setInterval` в Netlify не запускаются. При отсутствии `DATABASE_URL` облачный запуск завершается ошибкой, а не создаёт временную локальную базу.

## 1. Сохранить старые данные

Создать, проверить и скачать JSON-копию из действующей локальной CRM. Сохранить локальную базу и секреты отдельно. Архив исходников на GitHub не содержит рабочую базу.

## 2. Подготовить Supabase

Открыть SQL Editor проекта и выполнить содержимое [supabase-netlify.sql](./supabase-netlify.sql). SQL создаёт/обновляет только схемы CRM и закрывает доступ клиентским ролям. Пароль для SQL Editor не передаётся в код. Скрипт идемпотентен, но для уже заполненного облачного проекта перед обновлением необходима резервная копия. Рекомендуется выполнять до запуска сайта.

Установщик представляет собой один атомарный `DO $karven_install$` блок: установка схемы поиска, создание таблиц, миграции и включение RLS выполняются внутри него. Вставляйте весь файл в новый запрос SQL Editor и выполняйте без выделенного фрагмента. При предупреждении редактора выбирайте Run without RLS: защиту включает сам блок.

Файл генерируется из той же схемы, что CLI: `npm run db:sql`. Альтернатива при защищённом серверном `DATABASE_URL`: `npm run db:migrate`, затем `npm run db:check`. Не выполняйте миграции в Netlify build: сборки и превью не должны менять рабочую базу.

## 3. Создать сайт Netlify

Импортировать GitHub-репозиторий `rusmp06-ai/Karven`. Настройки сборки уже в `netlify.toml`: `npm run build`, каталог `.next`, Node.js 24. Netlify должен применить поддерживаемый адаптер Next.js; не выбирать ручной статический экспорт.

До запуска production добавить через **Environment variables** (серверные, для Functions, только Production):

| Переменная | Значение |
| --- | --- |
| `CRM_DEPLOYMENT` | `netlify` |
| `DATABASE_URL` | PostgreSQL URI из Session pooler с URL-кодированным паролем |
| `CRM_ADMIN_USER` | Логин первоначального владельца; при переносе совпадает с логином в копии |
| `CRM_ADMIN_PASSWORD` | Длинный уникальный пароль владельца |
| `CRM_COOKIE_SECURE` | `true` |
| `CRM_TELEGRAM_KEY` | Постоянный секрет: 64 шестнадцатеричных символа (32 случайных байта) |

Структура строки подключения, без действительного пароля:

```text
postgresql://postgres.nouhzimocqsquztiqwut:ENCODED_PASSWORD@aws-0-ap-southeast-2.pooler.supabase.com:5432/postgres
```

Сгенерировать ключ на доверенном компьютере один раз:

```sh
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Секреты не отправлять в чат, не коммитить и не создавать переменные `NEXT_PUBLIC_` с этими значениями. Не выдавать production-переменные Deploy Preview и сборкам недоверенных веток. Сборке значения базы/пароля не нужны. Для Supabase в приложение включён публичный Supabase Root 2021 CA (до 26 апреля 2031), скачанный из настроек проекта. Он добавляется к стандартным корневым сертификатам только для доменов `.pooler.supabase.com` и `.supabase.co`; проверка сертификата и имени сервера остаётся включённой. Переменная `PGSSLROOTCERT_PEM` обычно не нужна.

При необходимости другого CA можно задать `PGSSLROOTCERT_PEM` для Functions с полным PEM или `PGSSLROOTCERT` с путём к файлу на обычном сервере. Такое явное переопределение имеет приоритет; повреждённый PEM вызывает ошибку, а не отключает TLS. Если после ручного ввода появилось «Не удалось прочитать сертификат PostgreSQL», удалите переменную `PGSSLROOTCERT_PEM` в Netlify и повторно разверните сайт, чтобы использовать встроенный сертификат. DATABASE_URL и остальные настройки сохраняются.

## 4. Первый запуск и перенос

После развёртывания открыть HTTPS-адрес сайта и войти владельцем. При пустой базе владелец создаётся автоматически. Импортировать локальную JSON-копию, проверить и восстановить её; затем войти повторно. Пароль текущего владельца сохраняется. Telegram и сеансы из копии не переносятся: подключить бота заново через настройки. Для существующего зашифрованного токена нужно сохранить старый 32-байтный ключ в виде hex либо заново ввести токен.

Проверить клиентов, рейсы, суммы, долги и отчёты. Создать облачную копию, скачать её и проверить доступность после повторного развёртывания. Проверить тестовое сообщение Telegram, новую бронь и расписание в разделе Functions. Исходные локальные данные до подтверждения результата не удалять.

## Лимиты бесплатного размещения

Бесплатность зависит от текущего тарифа аккаунтов и нагрузки; лимиты необходимо сверить в кабинетах Netlify и Supabase. Сборки, функции, расписание, трафик, база и архивы расходуют квоты. Supabase может приостанавливать неактивные проекты. Исчерпание квоты может остановить сайт или уведомления. Перед реальной эксплуатацией нужно проверить условия аккаунтов; автоматическая платная докупка ресурсов не настраивается этим кодом.

Блокировка всех запросов снижает пропускную способность ради сохранения текущих гарантий. Время функций ограничено: большая копия или медленное внешнее соединение может не уложиться в него. Начинать следует с пробного запуска и небольшого объёма данных. При прерывании копия остаётся с незавершённым статусом, а замена рабочих данных выполняется транзакционно.

## Проверки разработчика

`npm run typecheck`, `npm test`, `npm run build`. Интеграционные PostgreSQL-тесты требуют только отдельный локальный сервер на `127.0.0.1:55439` через `KARVEN_PG_TEST_URL` и сами создают/удаляют новую тестовую базу. Браузерные проверки могут использовать отдельную PostgreSQL через `KARVEN_E2E_PG_URL` (тот же локальный порт, новая база с префиксом `karven_e2e_`), включая режим `CRM_DEPLOYMENT=netlify`. Реальные облачные реквизиты для тестов не использовать.


## Восстановление после EMAXCONNSESSION

Сначала опубликуйте исправленную версию с управлением соединениями на время запроса. Старые замороженные экземпляры могут оставлять сессии предыдущей версии. При необходимости выполните в Supabase SQL Editor:

```sql
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE datname = current_database()
  AND application_name = 'karven-crm'
  AND state = 'idle'
  AND state_change < now() - interval '2 minutes'
  AND pid <> pg_backend_pid();
```

Запрос закрывает только бездействующие более двух минут соединения CRM в текущей базе. Он не удаляет таблицы или данные и не выбирает активные запросы либо незавершённые транзакции. Пустой результат означает, что подходящих соединений нет. Пароль, DATABASE_URL и порт 5432 менять не требуется. После очистки обновите сайт. Не выполняйте массовое отключение всех соединений проекта.


## Скорость сохранения

Независимые чтения главной страницы, финансов, карточек клиентов, парка и Telegram запускаются одновременно через конвейер `pg` по одному закреплённому соединению. Это сокращает последовательные ожидания сети без увеличения числа сессий и без преобразования типов PostgreSQL в JSON. Даты и точные bigint сохраняют прежнее представление. При входе в CRM сгруппированы независимые операции, а повторная инициализация существующего владельца не открывает лишнюю транзакцию. В создании брони уменьшено число обращений к базе; проверки вместимости и предоплаты остаются атомарными.

Интеграционная проверка с искусственной задержкой 40 мс в каждую сторону сравнивает восемь последовательных чтений с конвейерными. В отдельном запуске: 669 мс против 126 мс. Это измерение сетевой части на тестовой базе, а не обещание такого же ускорения всей страницы Netlify. Холодный запуск, расстояние до Supabase, объём данных и ожидание блокировки продолжают влиять на время ответа.


## Диагностика ожидания блокировки

Если после публикации появляется сообщение об ожидании блокировки, выполните этот запрос в SQL Editor и передайте результат для диагностики. Запрос ничего не изменяет и не выводит текст бизнес-запросов либо пароли:

```sql
SELECT a.pid, a.application_name, a.state,
       now() - a.state_change AS state_duration,
       l.granted
FROM pg_stat_activity a
JOIN pg_locks l ON l.pid = a.pid
WHERE a.datname = current_database()
  AND l.locktype = 'advisory'
  AND l.objid = 746376002;
```

Ошибка лимита соединений и ожидание блокировки теперь различаются в серверном журнале. Это помогает выбрать дальнейшие действия по фактическому состоянию, без смены паролей и повторного создания базы.
