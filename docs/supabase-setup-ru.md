# Подключение Supabase PostgreSQL

Проект: https://supabase.com/dashboard/project/nouhzimocqsquztiqwut

Адрес `https://nouhzimocqsquztiqwut.supabase.co/rest/v1/` и ключ `sb_publishable_…` относятся к HTTP API. Они не заменяют PostgreSQL-подключение. CRM использует собственные серверные учётные записи и SQL-транзакции; Supabase Auth подключать не требуется.

## Что взять в Supabase

1. Открыть проект и кнопку **Connect** в верхней панели.
2. Выбрать **Session pooler**, обычно порт **5432**. Transaction pooler на 6543 для текущего приложения не подходит.
3. Посмотреть Host, Port, Database, User. Эти четыре значения можно передать без пароля.
4. Пароль базы и полную строку с ним добавлять только в защищённые серверные настройки или игнорируемый `.env.local`. Не отправлять в чат и не использовать переменную с префиксом `NEXT_PUBLIC_`.

Пример структуры, не рабочие реквизиты:

```dotenv
DATABASE_URL=postgresql://postgres.PROJECT_REF:ENCODED_PASSWORD@SESSION_POOLER_HOST:5432/postgres
```

Если пароль содержит специальные символы, они должны быть URL-кодированы. При требовании собственного корневого сертификата провайдера задаётся `PGSSLROOTCERT` с путём к доверенному CA. Проверка TLS для удалённых серверов включена и не отключается через параметры URL.

## Подготовка и переключение

1. На локальной версии создать и проверить резервную копию через настройки, скачать её и сохранить отдельно. Сохранить рабочую папку PGlite и локальные секреты.
2. Остановить сервер приложения. Добавить серверный `DATABASE_URL` в `.env.local` или защищённые переменные среды.
3. Выполнить `npm run db:migrate`. Команда создаёт/обновляет только схему `karven` и не переносит данные автоматически. Для существующей базы предварительно требуется её резервная копия.
4. Выполнить `npm run db:check` — проверка соединения и версии схемы.
5. Запустить `npm run build`, затем `npm start`. Первый владелец создаётся только в пустой базе по CRM_ADMIN_USER/CRM_ADMIN_PASSWORD. Для переноса логин должен совпадать с владельцем в резервной копии.
6. Войти, загрузить сохранённый JSON через «Резервные копии», проверить и восстановить его. Текущий пароль владельца сохранится; после восстановления нужен повторный вход. Настройки Telegram и очередь не переносятся, их надо настроить заново.
7. Сверить клиентов, рейсы, оплаты, долги, расчёты и отчёты. Старую локальную базу и файл копии не удалять до подтверждения результата.

Без DATABASE_URL работает прежняя локальная PGlite. При заданном DATABASE_URL ошибка серверного подключения не включает скрытый откат на локальную базу. Для возврата к локальной базе нужно остановить приложение, убрать DATABASE_URL и запустить снова; учитывайте, что новые данные серверной базы автоматически в старую локальную базу не копируются.

## Доступ и эксплуатация

SQL выполняется сервером через `pg`, данные лежат в закрытой схеме `karven`. У ролей PUBLIC, anon, authenticated, service_role нет доступа к таблицам CRM; дополнительно включён RLS без клиентских политик. Опубликованный клиентский ключ Supabase не используется для запросов CRM. Не добавляйте `karven` в открытые API-схемы и не выдавайте клиентским ролям права к ней.

Текущая архитектура рассчитана на один постоянно работающий сервер приложения и много сотрудников в браузерах. Сервер удерживает отдельную сессионную блокировку: второй сервер или миграция во время работы первого не запускаются. При потере этой сессии требуется перезапуск. Бизнес-транзакции сериализуются транзакционной advisory-блокировкой PostgreSQL: сохранены гарантии бронирований, оплат и назначений. Горизонтальное масштабирование и serverless-развёртывание пока не поддерживаются, поскольку также используются локальные ключи, копии и фоновая очередь Telegram.

Серверу нужен TCP/TLS-доступ к выбранному pooler host:5432. HTTP-разрешение домена в облачном прокси не гарантирует доступ к PostgreSQL. Проверка на настоящем Supabase выполняется после получения серверных параметров и безопасного ввода пароля.

## Проверка на изолированном PostgreSQL

`tests/postgres.test.ts` проверяет PostgreSQL 17, изоляцию схемы, отсутствие доступа anon, откат, конкурентные бронирования/оплаты и переносимость копий. Интеграционные тесты запускаются только при `KARVEN_PG_TEST_URL` и разрешают исключительно отдельную локальную тестовую PostgreSQL на 127.0.0.1:55439. Они создают новую базу с префиксом `karven_test_` и удаляют её после завершения. Реальный DATABASE_URL для этих тестов не используется.
