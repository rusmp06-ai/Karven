# Архитектура Karven

## Текущая реализация (0.5)

Next.js App Router, TypeScript, Zod, PostgreSQL через PGlite в одном процессе. Серверные действия проверяют сессию из HttpOnly-cookie, затем передают доверенного `Actor` в прикладные сервисы. Роль или ID сотрудника из формы не принимаются как доказательство полномочий. Каждый сервис проверяет допустимые роли, запросы кабинета водителя фильтруются по `actor.driver_id` до отправки данных браузеру.

- `src/lib/crm.ts`: рейсы, клиенты, бронирования и оплаты.
- `src/lib/fleet.ts`: водители, автомобили, назначения и ограничения ресурсов.
- `src/lib/finance.ts`: завершение рейсов, возвраты, расходы, утверждения и выплаты, агрегаты по каждому рейсу.
- `src/lib/idempotency.ts`: квитанции повторных запросов в одной транзакции с операцией.
- `src/lib/trip-operations.ts`: перенос, состав группы, индивидуальные отметки, отмена рейса и полный возврат по активным заказам.
- `src/lib/auth.ts`: scrypt-пароли, первоначальный владелец, вход, сессии, сотрудники, блокировки и сброс паролей.
- `src/lib/session.ts`: получение действующего сотрудника для запроса, перенаправление на вход.
- `src/lib/audit.ts`: события с авторством. Пароли и токены в журнал не попадают.
- `src/lib/schema.ts`: неизменная версия 1 и атомарные миграции 2–5 с реестром применений.

Сущности: clients → bookings ← trips; bookings → payments. trips ссылаются на drivers и vehicles. users могут ссылаться на driver; sessions привязаны к users, audit_events — к автору. Один водитель может иметь одну учётную запись. Удаление финансовых операций и сотрудников не предусмотрено; доступ блокируется.

Деньги — целые minor units. Баланс и занятость вычисляются. Бронирования, платежи и назначения проверяются в транзакциях вместе с записью аудита. PGlite сериализует транзакции; блокировки строк выражают намерение при будущем переходе на сервер PostgreSQL. До перехода нужны интеграционные тесты на нескольких соединениях, единый порядок блокировок и ограничение пересечения ресурсов на уровне БД. Текущий драйвер PGlite нельзя запускать несколькими процессами с одной папкой.

Назначение обновляет пассажирскую вместимость рейса. Проверяются проданные места, статус водителя/машины, удостоверение до локальной даты окончания и пересечения `[departure_at, ends_at)`. Время возвращения/отдыха включается диспетчером в плановый интервал. Изменение статуса ресурса защищает существующие активные назначения. Отмена брони освобождает места, но не освобождает ресурсы рейса.

## Решения для следующих этапов

1. Сервер PostgreSQL, управляемые миграции, автоматические резервные копии с тестом восстановления и мониторинг.
2. Временное удержание брони, управление клиентской базой, задачи, напоминания и справочники тарифов.
3. Корректировки утверждённых расчётов, сторнирование выплат, расчёты с владельцами автомобилей, сбор и сдача наличных водителем. Разные валюты не суммируются без явного курса.
4. Самостоятельная смена пароля, многофакторная защита владельца, управление ролями существующих записей и детализированные разрешения.
5. Загрузка и сроки документов автомобилей, задачи, уведомления, отчёты и интеграции по доступным API.

Текущее правило: частичный возврат уменьшает и начисление, и полученные деньги; отмена с возвратом полностью закрывает бронь. Вознаграждение водительское — явно введённая владельцем сумма без автоматической комиссии. Для утверждённых расчётов расходы фиксируются. Возвраты после утверждения изменяют результат парка, но не меняют согласованное вознаграждение. Правила комиссий, штрафов и расчётов с владельцами автомобилей необходимо согласовать с владельцем бизнеса перед реализацией. Текущий этап не заявляет готовность к производственной эксплуатации.


## Финансовые операции

`refunds` хранит неизменяемые возвраты, `trip_expenses` — расходы с мягким аннулированием, `driver_settlements` — единственный утверждённый расчёт по рейсу, `driver_payouts` — выплаты. Цена в `bookings.total_minor` исходная; эффективная цена активной брони вычитается из возвратов, отменённой равна 0. Полученная оплата — платежи минус возвраты. Это исключает возникновение долга из-за согласованной скидки-возврата.

`mutation_receipts` связывает UUID запроса, сотрудника, тип операции и SHA-256 нормализованного содержимого. Вставка квитанции и изменение финансов проходят одной транзакцией. Совпавший запрос возвращает успех без повторной записи, другой payload с тем же ключом отклоняется. UI передаёт ключ и меняет его после успешного ответа; старый вызов платежа без ключа поддержан сервисом для совместимости, но такой вызов не даёт гарантии повторной отправки. Клиент не передаёт валюту/водителя для выплаты: они определяются рейсом и утверждённым расчётом.

Агрегаты формируются из отдельных подзапросов до JOIN, поэтому множество оплат, возвратов и расходов не умножает суммы. Показатели парка заменяются на null до отправки ответа водителю, списки также фильтруются на сервере. Право возврата, утверждения, аннулирования расхода и выплаты есть только у владельца. Диспетчер может завершать рейсы и учитывать расходы.

Для серверного PostgreSQL необходимо дополнить атомарную обработку ключей повторных запросов (unique insert с обработкой конфликта) и проверить единый порядок блокировок: текущая PGlite-реализация сериализует транзакции. Завершение освобождает ресурсы рейса; начисления и долги пассажиров остаются, отмена брони после завершения запрещена. Финансовые изменения после завершения фиксируются в аудите.


## Данные заказа

Миграция 4 добавляет в bookings снимок контакта заказчика, JSONB пассажиров, тип заказа, фактическое число пассажиров, адреса, багаж, детские кресла и источник. `src/lib/orders.ts` содержит общие серверные валидаторы. Для новых UI-заказов список пассажиров должен соответствовать фактическому числу; для совместимости старые сервисные вызовы без списка поддерживают известный контакт и не выдумывают имена остальных. Редактирование требует заполнить полный список и не меняет цену/резерв.

`bookings.seats` — резервируемая вместимость, `passenger_count` — число людей. Для заказа всей машины они могут различаться. Проверка вместимости и создание заказа идут в одной транзакции с блокировкой рейса. При замене автомобиля эксклюзивная бронь занимает новую вместимость, проверяется число пассажиров; обычные брони проверяются по сумме мест. Отменённые брони не блокируют места. Контакты в заказе не изменяют исторические контакты других заказов.

Диспетчерские фильтры работают поверх серверной выборки, уже ограниченной правами. Адреса и пассажиры выдаются назначенному водителю, источник и внутренние заметки скрыты. Для больших объёмов данных предстоит серверная пагинация и поиск; текущая локальная версия загружает доступные записи целиком.


## Состояния поездки

Миграция 5 расширяет `trips.status` значением cancelled, добавляет причину/время отмены и `passenger_attendance` с ключом `(booking_id, position)`. Отсутствие строки означает pending; строка содержит boarded/no_show и автора последнего изменения. Все переходы также записываются в audit_events. Удаление строки при исправлении в pending не удаляет историю события.

Перенос блокирует бронь и оба рейса в порядке их ID, проверяет направление, валюту, время и вместимость. Передача меняет только trip_id и резерв мест. Финансовые операции остаются на том же booking_id, отчёты агрегируют их по текущему рейсу. Изменение числа пассажиров сохраняет исходную цену и запрещается при отметках. При всей машине резерв равен вместимости целевого рейса, независимо от числа людей.

Посадка возможна с departure_at−2h, неявка с departure_at. Водитель может только впервые отметить пассажира собственного рейса. Менеджер исправляет с причиной, закрытые рейсы защищены. Отметки блокируют замену водителя/машины, изменение карточки, перенос и отмену. Завершение требует обработать все позиции всех подтверждённых заказов.

Отмена рейса блокирует рейс и активные брони, проверяет роль, записывает остаточные возвраты и отменяет брони атомарно. Метод возврата указывается для всей операции; фактическая передача денег подтверждается человеком. Старые расходы и привязки водителя/машины сохраняются для истории, ресурсы освобождаются через исключение cancelled из активных назначений. Утверждение расчёта разрешено и для cancelled, чтобы не потерять возмещение расходов водителя. Неявка не несёт автоматических финансовых изменений.

Функции используют существующий механизм ключей повторных запросов. Для будущего серверного PostgreSQL остаются обязательны проверка общего порядка блокировок всех финансовых/операционных команд и обработка конфликтующих insert ключей на нескольких соединениях. В текущем PGlite транзакции сериализованы.


## Представление по согласованному макету

`ui.tsx` управляет навигацией и выбором рейса, `dispatch.tsx` — расписанием/списком и инспектором, `icons.tsx` — локальными SVG-иконками, `modal.tsx` — нативным dialog с фокусом и Escape. Существующие операционные формы переиспользуются в модальных окнах и карточках без замены бизнес-логики. Создание рейса больше не занимает постоянную колонку расписания.

`/demo` использует фиксированные примеры из `demo/data.ts` без чтения рабочей базы и авторизации. DemoContext блокирует сохранение всех форм, включая модальные. Публичная страница не получает пользователей или данные рабочего сервера. Клиентские показатели рабочих экранов вычисляются из авторизованной выборки. Отдельная серверная агрегация дат платежей/возвратов ограничивается собственными рейсами для роли водителя; суммы по разным валютам не смешиваются.

Клиенты, отчёты и задачи в этой версии — представления уже доступных записей. Отдельные CRUD для клиентского профиля, поручений и настроек тарифов остаются следующими этапами. Индикатор мест визуализирует вместимость, не выдавая резерв мест за закрепление сидений.
